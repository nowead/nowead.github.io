## 현장의 문제

아마추어 축구팀은 매주 경기를 하지만, 운영은 대부분 사람의 기억과 메신저에 기대고 있습니다. 서비스 오너와 함께 정리한 문제는 세 가지였습니다.

- 참석, 명단, 매칭 주선을 **흩어진 도구로 수동 관리**해 누가 팀에 기여했는지 추적하기 어렵습니다.
- 기여가 득점과 도움 위주로만 이야기되어, 꾸준한 출석이나 감독 역할 같은 **경기 밖의 기여가 드러나지 않습니다.**
- 경기 기록이 남지 않거나 **믿기 어려워**, 개인과 팀의 히스토리가 쌓이지 않습니다.

onegoal은 이 문제를 풀기 위한 웹 서비스입니다. 팀 관리, 출석, 쿼터별 라인업, 경기 기록과 승인, 통계를 한곳에서 다룹니다.

## 문제 정의: 요청을 요구사항으로

### 제품 문서가 단일 출처

코드를 쓰기 전에 제품 문서(PRD)와 요구사항 명세서를 먼저 만들었습니다. PRD에는 대상 사용자와 핵심 시나리오 5개, 그리고 만들지 않을 것(네이티브 앱, 팀 간 리그 등)을 적었습니다. 기능의 동작 규칙은 `FR-MATCH-7`처럼 번호가 붙은 요구사항으로만 정의합니다. 현재 정의된 요구사항은 **129개**이고, 모든 테스트는 자신이 검증하는 요구사항 번호를 명시합니다.

제품이 실제로 돌고 있는지 판단하는 기준도 먼저 정했습니다. 북극성 지표는 "주간 승인 완료 경기 기록 수"입니다. 활동 → 기록 입력 → 관리자 승인 → 통계 반영으로 이어지는 핵심 흐름이 끊기지 않는지를 보기 위한 지표입니다.

### 한 줄짜리 요청에는 확인 질문부터

운영을 시작한 뒤에는 오너의 요청이 한꺼번에 들어왔습니다. 2026년 10월 22일에는 12개의 요청을 한 번에 받았고, 항목마다 현재 상태(이미 됨 / 이번에 구현 / 정의 필요)를 나눈 뒤 요구사항 번호를 붙였습니다.

| 받은 요청 | 정의한 내용 | 요구사항 |
| --- | --- | --- |
| "내전" 경기 형태 | 상대 팀 없이 팀원과 용병을 편으로 나눠 치르는 경기. 이후 2~4개 편으로 확장 | FR-MATCH-36 |
| 경기 생성은 누구나 | 팀원이 등록하고, 관리자가 승인해야 공식 일정이 되는 검토 흐름 | FR-MATCH-37 |
| "fan 기능" | 계정을 가진 팬이 팀을 팔로우해 일정·결과를 열람. 출석 기록은 비공개 | FR-TEAM-20 |
| "팀 중복 처리" | 같은 이름을 허용하되 팀 코드로 구분하고, 팀 생성은 운영자 승인 | FR-TEAM-21 |

"fan 기능"처럼 한 줄뿐인 요청은 바로 구현하지 않았습니다. 팬에게 계정이 필요한지, 어디까지 볼 수 있는지, 가입에 승인이 필요한지, 팬 수를 표시할지 **네 가지 확인 질문**을 먼저 보냈습니다. "팀 중복 처리"는 "중복"이 가리킬 수 있는 대상을 네 가지 후보로 나눠 제시했습니다. 같은 날 저녁 답변을 받은 뒤에 설계 문서를 쓰고 구현했습니다.

### 결정은 기록으로

구현 방식을 바꾸는 결정은 ADR(Architecture Decision Record)로 남겼습니다. 선택한 방법과 버린 대안, 근거를 함께 적습니다. 지금까지 **42건**이 쌓였고, 결정을 바꿀 때는 기존 기록을 고치지 않고 이전 기록을 대체하는 새 기록을 추가합니다.

## 해결: 경기 하루를 따라가는 화면

### 쿼터별 라인업 추천

동호회 경기는 여러 쿼터로 나뉘고, 참석한 모두가 고르게 뛰어야 합니다. 관리자가 매번 손으로 짜던 쿼터별 명단을 자동으로 추천하는 기능을 만들었습니다.

첫 구현은 쿼터마다 따로 최적 배정을 구하는 방식이었습니다. 실제 팀의 13개 경기일 데이터에 적용해 보니, 주 포지션이 아닌 자리에 서는 경우가 선수·쿼터 기준 **74건** 남았습니다. 숫자로 확인한 뒤 방법을 두 번 바꿨습니다.

| 단계 | 방법 | 포지션 불일치 |
| --- | --- | --- |
| 1 | 쿼터마다 따로 최적 배정 | 74건 |
| 2 | 전체 쿼터를 한 번에 계획 | 68건 |
| 3 | 최소 비용 흐름으로 다시 모델링하고, 포메이션이 참석 명단을 따르도록 변경 | **36건** |

최종 방식에서도 출전 시간 차이는 1쿼터 이내로 유지되고, 계산은 약 80ms에 끝납니다. 이 과정은 두 건의 ADR에 수치와 함께 남아 있습니다.

### 기록은 승인 후에만 통계가 된다

"기록을 믿기 어렵다"는 문제는 검토 흐름으로 풀었습니다. 팀원이 입력한 경기 기록은 `검토 대기` 상태로 시작하고, 관리자가 승인하거나 반려합니다. 승인한 기록만 통계와 보상에 반영되고, 승인된 경기를 삭제하면 반영됐던 내용도 함께 되돌립니다.

### 경기장에서 보는 실시간 스코어보드

경기 중에는 기록 담당자가 저장한 내용이 팀원의 화면에 5초마다 갱신됩니다. 경기장에서 휴대폰으로 보는 화면이기 때문에 모바일 폭을 기준으로 설계했고, 홈 화면에 설치할 수 있는 PWA로 제공합니다. 경기가 끝나면 종합 스코어와 득점 선수, 경기 후 선수 투표로 이어집니다.

### 구조: 모듈러 모놀리식과 순수 도메인 코어

1인 개발로 유지할 수 있는 구성을 목표로 했습니다.

- **Django 5.2 LTS 서버 렌더링**과 프레임워크 없는 JavaScript 모듈로 화면을 만들었습니다. 빌드 단계가 없어 배포가 단순합니다.
- 라인업 추천, 시너지 계산 같은 규칙은 **프레임워크에 의존하지 않는 순수 도메인 코어**에 두었습니다. 데이터베이스 없이 빠르게 테스트할 수 있습니다.
- 이 경계는 하네스가 검사합니다. 도메인 코어가 Django나 입출력 모듈을 import하거나, 뷰가 직접 트랜잭션을 열면 검증이 실패합니다.
- 로그인은 이메일 인증과 카카오·구글·네이버 소셜 로그인을 지원하고, 운영자 계정에는 TOTP 2단계 인증을 요구합니다.

## 검증: 테스트를 통과해야 완료

### 읽기 전용 테스트 하네스

구현에는 AI 코딩 에이전트를 활용했습니다. 그래서 "무엇이 완료인가"를 코드보다 먼저, 사람이 고정해 두어야 했습니다. 규칙은 단순합니다.

1. 요구사항을 정하고, **수용 테스트를 코드보다 먼저** 작성합니다.
2. 검증 단계에서 `tests/`는 읽기 전용입니다. 테스트를 고쳐서 통과시킬 수 없습니다.
3. 검증은 `./harness/verify.sh` 하나로만 실행합니다. Docker 안에서 돌려 실행 환경의 차이를 없앴습니다.

2026년 11월 6일 기준 전체 하네스 결과입니다.

| 항목 | 결과 |
| --- | --- |
| 요구사항 추적 | 129개 중 125개가 테스트로 검증됨, 4개는 사유와 함께 보류 |
| 테스트 (PostgreSQL) | 1,439개 통과 · 8개 건너뜀 |
| 테스트 (SQLite) | 1,437개 통과 · 10개 건너뜀 |
| 커버리지 | 96.98% (하한 90%) |
| 운영 구성 | 운영 이미지, PostgreSQL, HTTPS, 복구 점검 통과 |

테스트가 늘면서 전체 검증이 약 20분까지 길어졌습니다. 테스트 전용 비밀번호 해시 설정을 분리해 3분 37초로 줄였습니다. 검증이 느리면 건너뛰고 싶어지기 때문에, 검증 속도도 관리 대상으로 봤습니다.

### 화면도 테스트한다

서버 테스트는 화면이 깨진 것을 잡지 못합니다. 그래서 주요 화면을 데스크톱·모바일, 밝은 테마·어두운 테마로 촬영해 기준 이미지 **132장**과 비교하는 게이트를 추가했습니다.

- 브라우저 버전을 고정하고 시계를 멈춰, 같은 코드면 같은 화면이 나오게 했습니다.
- 바뀐 픽셀이 0.05%를 넘거나, 화면 크기가 달라지거나, 기준 이미지가 없으면 실패합니다.
- 의도한 디자인 변경은 같은 PR에서 기준 이미지를 함께 갱신합니다.

### 운영 환경과 같은 구성으로 점검

배포 직전의 사고는 대부분 코드가 아니라 구성에서 납니다. 하네스의 마지막 단계는 운영용 이미지를 실제로 띄워 프록시, 정적 파일, 미디어 파일, HTTPS 응답을 확인하고, 데이터베이스와 미디어 백업을 한 쌍으로 복구해 봅니다.

| 웹 | Cloudflare → Caddy(자동 HTTPS) → Gunicorn(비 root 실행) |
| 데이터 | PostgreSQL 17 · Redis · 비공개 S3(미디어와 백업) |
| 계정 보호 | 이메일 인증 · 운영자 TOTP · Redis 기반 요청 제한 |
| 관측 | Better Stack 5분 간격 점검 · 백업 완료 신호 · Sentry 오류 수집 |

데이터베이스, Redis, Gunicorn 포트는 외부에 열지 않았습니다. 운영 배포는 매번 오너의 승인을 받은 뒤에 진행합니다. 2026년 11월 6일 기준으로 가입자 34명, 실제 아마추어 축구팀 한 곳이 선수 29명과 14경기를 기록하고 있습니다. 규모는 작지만, 실제 경기일마다 쓰이는 서비스입니다.

## 피드백이 다시 요구사항으로

배포는 끝이 아니라 다음 요청의 시작이었습니다. 쿼터별 편 배정을 한 화면의 표로 보여 주던 내전 설정은 "너무 많고 복잡하다"는 피드백을 받았습니다. 표를 걷어내고 쿼터마다 필요한 조정만 하는 버튼으로 바꿨습니다. 요청은 다시 요구사항이 되고, 요구사항은 테스트가 되고, 테스트를 통과한 변경이 배포됩니다.

## 이전 프로젝트에서 이어진 것

onegoal은 처음 만든 웹 서비스가 아닙니다. 앞선 두 프로젝트에서 직접 구현해 본 것들이 판단의 근거가 됐습니다.

- **[WebServ](/fde/webserv/)** — HTTP 서버를 소켓부터 구현해 본 경험이 리버스 프록시가 넘기는 헤더, 클라이언트 IP 신뢰 범위, 워커 프로세스 구성 같은 운영 구성을 프로토콜 수준에서 판단하는 기준이 됐습니다.
- **[ft_transcendence](/fde/ft_transcendence/)** — OAuth 로그인과 2단계 인증, 프레임워크 없는 프런트엔드, API 계약을 먼저 맞추는 협업 방식이 onegoal의 인증 구성과 "명세 먼저" 개발 방식으로 이어졌습니다.
